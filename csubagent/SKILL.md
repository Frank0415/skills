# csubagent

让主 Agent 作为协调者留在用户对话中，把实质性、独立且边界明确的工作交给 subagent。目标是提高完成质量和并行效率，并保护主线程中的需求、决定和最终输出。

主动寻找适合委派的工作。满足本技能的委派条件时，不要等待用户再次要求“开 subagent”。委派不扩大用户授权，也不以增加 agent 数量为目标。

## 成功条件

一次 subagent 工作流完成时，应满足：

- 主 Agent 始终掌握用户目标、任务状态、权限边界和最终交付；
- 每个 subagent 有明确且互不重叠的所有权；
- subagent 返回提炼后的证据、改动和验证结果，不向主线程倾倒原始过程；
- 并行工作没有引入未处理的写入冲突或相互矛盾的结论；
- 主 Agent 已综合结果、处理冲突并验证最终输出；
- 所有 subagent 的 reasoning effort 不低于 `medium`。

## 判断是否委派

当以下任一条件成立，并且存在可独立推进的工作面时，积极委派：

- 任务包含两个或更多可以同时推进的调查、审查、测试或实现工作面；
- 探索笔记、测试日志、堆栈信息或资料摘录可能污染主线程上下文；
- 一个大型代码库、文档集或数据集可以按语义边界拆成独立输入；
- 主 Agent 可以继续处理关键路径、用户沟通或结果整合，同时 subagent 完成辅助工作；
- 专项工作需要不同关注点，例如安全、正确性、测试、文档、兼容性或视觉验证；
- 独立复核能显著降低遗漏、错误假设或单一路径判断的风险。

以下情况通常不委派：

- 任务很小，主 Agent 可以用少量直接操作完成；
- 下一步严格依赖当前结果，无法形成真正独立的工作面；
- 工作高度耦合，拆分后需要频繁同步才能保持正确；
- 多个 agent 必须同时修改相同文件、状态或外部资源；
- 委派的协调成本预计高于速度、质量或上下文收益。

不要因为任务困难而自动委派。先判断是否存在可单独交付和验证的工作面。存在合理的并行收益时，倾向于委派；不要仅因收益无法精确量化而放弃。

## 主 Agent 职责

主 Agent 必须：

1. 确认用户可见结果、范围、证据和完成标准。
2. 识别关键路径、独立工作面及依赖关系。
3. 为每个 subagent 指定清楚的所有权和交付物。
4. 在 subagent 工作期间继续处理不重叠的主线工作，或保持可响应用户。
5. 路由必要的补充指令和跨 agent 依赖信息。
6. 在需要同步的节点等待结果，而不是频繁轮询。
7. 综合证据，解决冲突，完成最终验证和用户答复。
8. 保留审批、外部副作用和重大决策的控制权。

主 Agent 不得把任务拆完后停止思考。Subagent 的结论是输入，不是自动成立的最终判断。

## 角色与推理强度

优先使用同一模型系列，仅按工作难度调整 reasoning effort。用户、项目配置或现有 agent 配置指定模型时，遵守该指定。

### Scout

使用 Scout 回答窄范围、只读的问题，例如：

- 定位文件、符号、入口或测试；
- 追踪调用路径或状态流；
- 检索文档、事实和版本行为；
- 检查日志、输出或一组独立材料；
- 为实现者整理所需证据。

Scout 应使用 `reasoning_effort: "medium"` 或更高。窄范围调查优先使用 `fork_turns: "none"`，避免继承无关历史。任务需要先前决定时，提供必要摘要或选择性继承相关上下文。

### Worker

使用 Worker 完成范围明确的实施、检查或支持工作，例如：

- 修改一个独立模块或互不重叠的文件集合；
- 运行并解释针对性测试；
- 完成一份独立文档或一个语义完整的文档组；
- 根据已确认的问题实施修复并验证。

常规工作使用 `reasoning_effort: "medium"`。涉及较深依赖、复杂逻辑、重要边界或困难验证时使用 `high` 或更高。

### Smart Worker

使用 Smart Worker 处理困难实施、歧义消解或需要有限协调的独立工作面。Smart Worker 应使用 `reasoning_effort: "high"` 或更高。

只有明确赋予协调职责的 Smart Worker 才可以继续委派。普通 Scout 和 Worker 是叶子 Agent，必须直接完成分配，不得生成其他 agent。

### 推理下限

所有 subagent 必须使用 `medium`、`high`、`xhigh`、`max` 或 `ultra`。不得使用 `low` 或任何低于 `medium` 的等级。缺省配置可能低于 `medium` 或无法确认时，生成 subagent 时显式指定 `medium` 或更高。

不要全局使用最高等级。先按任务难度选择最低充分等级，再根据歧义、风险、依赖深度或失败证据提高 effort。

## 编写委派任务

每个委派任务应包含完成该任务所需的最小充分信息：

- **目标**：subagent 必须产出的结果；
- **所有权**：负责的文件、模块、问题、文档或证据范围；
- **输入**：权威路径、资料、已有决定和必要上下文；
- **边界**：不得修改或不得推断的内容；
- **输出**：应返回的证据、文件改动、测试结果或结构；
- **完成标准**：何时停止以及如何验证；
- **协作规则**：是否为叶子 Agent、是否允许联系其他 agent。

使用直接、可验证的任务说明。不要只写“研究一下”“看看有没有问题”或“帮忙处理”。不要把完整对话历史当成任务说明的替代品。

叶子 Agent 的任务中加入等价边界：

```text
直接完成本任务。不要生成其他 agent。只处理指定范围，并返回证据、结果和验证状态。
```

## 上下文策略

根据任务选择上下文继承方式：

- 对窄范围调查、独立验证和明确实现，优先使用 `fork_turns: "none"`；
- 对依赖用户偏好、既有决定或复杂计划的工作，可以继承必要对话；
- 对新鲜上下文 Agent，必须在任务中重复必要的安全、工具、权限、保留内容和验收边界；
- 对继承父上下文的叶子 Agent，必须明确父 Agent 的委派指令不适用于叶子 Agent。

不要让 Agent 继承大量无关历史。也不要为了获得干净上下文而省略决定正确性所需的信息。

## 并行与所有权

优先并行以下读密集型工作：

- 代码库探索；
- 测试、分类和日志分析；
- 文档或资料检索；
- 多角度审查；
- 独立材料的总结和证据提取。

并行写入必须满足以下条件：

- 每个 Worker 拥有互不重叠的文件、模块、文档或状态；
- 接口和依赖已足够稳定；
- 每个工作面可以独立验证；
- 主 Agent 能在合并前检查交叉影响。

如果写入边界重叠、执行顺序影响结果或多个任务依赖同一未确定设计，改为串行，或先由 Scout 消除歧义。不要为了填满并发名额而拆分一个不可分割的论证、推导、状态迁移或实现。

并发数量由任务独立性、资源限制和配置共同决定。不要把文章中的示例并发数当成固定要求。优先使用足够完成独立工作面的最小并发数。

## Agent 间协作

允许 Agent 在发现真实依赖时直接传递信息。消息必须说明：

- 发现了什么；
- 证据在哪里；
- 为什么影响接收方；
- 接收方需要采取什么动作。

不要鼓励无目的的 agent 间讨论。主 Agent 继续跟踪所有权和整体状态。依赖改变任务范围、权限或关键设计时，必须回到主 Agent 处理。

## 运行与同步

1. 在确认存在独立工作面后尽早生成 subagent。
2. 生成后继续处理不重叠的关键路径、整合准备或用户沟通。
3. 仅在新证据改变任务、Agent 遇到阻塞或需要同步时发送补充指令。
4. 不要用高频轮询代替状态通知或合理等待。
5. 在最终结果依赖所有分配任务时，等待所需 Agent 完成。
6. 收到结果后先综合，再决定是否需要最小补充调查、修复或复核。
7. 关闭已经完成且不再需要的 Agent 工作。

不要重复执行 subagent 已经完成且有充分证据的工作。关键结论、外部副作用和高风险改动仍需主 Agent 按任务风险验证。

## 权限与安全

Subagent 继承主线程的沙箱和权限环境。主 Agent 必须把实时权限边界视为有效边界，不得假设自定义 Agent 配置能够扩大权限。

委派本身不授权：

- 用户只要求分析或计划时实施修改；
- 执行破坏性操作；
- 写入外部系统；
- 发布、发送、购买或改变访问权限；
- 扩大任务范围。

需要新审批的操作必须由主 Agent 保留给用户决定。不要让 subagent 通过间接路径绕过审批。

## 结果整合

要求 subagent 返回精炼结果，至少包括适用项：

- 已完成的工作；
- 关键发现及证据位置；
- 修改的文件或产物；
- 运行的验证及结果；
- 未解决的阻塞、风险或假设；
- 需要其他 Agent 或主 Agent 接手的依赖。

主 Agent 最终必须：

- 去除重复和无关过程；
- 区分事实、推断和建议；
- 解决或明确标记冲突；
- 核对改动和验证是否覆盖用户目标；
- 说明已完成内容和真实遗留问题。

不要把多个 subagent 回答直接拼接为最终答复。

## 自检

在生成 subagent 前检查：

1. 该任务是否有实质性且可独立交付的工作面？
2. 委派是否会提高速度、质量或主线程上下文质量？
3. 每个 Agent 的所有权是否明确且互不重叠？
4. 上下文、权限、输出和完成标准是否充分？
5. reasoning effort 是否至少为 `medium`？
6. 叶子 Agent 是否被明确禁止继续委派？

在最终交付前检查：

1. 所需 Agent 是否已经完成或被明确取消？
2. 主 Agent 是否综合并验证了结果，而不是盲目信任？
3. 是否处理了写入冲突、结论冲突和跨任务依赖？
4. 是否保留用户授权和审批边界？
5. 最终输出是否聚焦用户结果，而不是 agent 活动本身？
