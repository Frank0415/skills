# 中文手法

输入规格是中文时套用本档。合同结构与英文层相同；句子纪律针对中文自己的写法。项目已有术语、标识符和引用的错误原文保持原样。

## 先分类

| 类别 | 用途 | 写法 |
|---|---|---|
| **规范句** | 可测试的契约 | 一项要求、一个等级词、写出执行者、条件、可观察结果 |
| **操作句** | 告诉读者做什么 | 祈使；一句一个动作 |
| **说明句** | 解释事物是什么、做什么 | 一句一个主题 |

动手前先给每段分类。步骤里的备注按说明句写。

## 等级词

文档开头声明含义，全文只用这一套：

- `必须`：绝对要求
- `不得`：绝对禁止
- `应该`：强烈推荐；可以有合理例外
- `不应该`：通常禁止；可以有合理例外
- `可以`：允许，不构成要求
- `可选`：功能、字段或步骤不是必需项

`应该` 若有重要例外，把例外或判断条件写在同一条要求里。

项目规定使用 GB/T 的「应、宜、可」时，开头声明该词表，全文使用该词表。

双语规格首次出现可以并列 `MUST（必须）`、`SHOULD（应该）`、`MAY（可以）`。之后选定一种语言的等级词写完全文。

说明句和操作句用普通中文陈述事实。等级词留给规范句。

## 用语

- 一个概念只用一个名称，全文一致。
- 沿用项目正式术语。新术语首次出现时定义，或写入术语表。
- 产品名、API 名、类型名、字段名、枚举值、命令、路径、字面量和单位保持原样。
- 用直接动词：写「验证令牌」「删除文件」。
- 用具体名词：写「认证服务」。
- 「配置 / 设置 / 选项」选定一个，全文沿用。
- 短定语。多层「的」拆成短句，或改成「……的……」两次以内。
- 缩写可能不明确时，首次给出全称。项目已把缩写当作正式名称时直接使用。

### 套话改成事实

没有事实的短语直接去掉。

| 套话 | 写成 |
|---|---|
| 赋能、抓手、闭环、对齐、落地、打磨 | 具体动作或结果 |
| 进行……操作、加以、予以、做出 | 那个动词本身 |
| 众所周知、在此说明、随着……发展 | （去掉，直接说事） |
| 无缝、强大、完善、全面、高效、便捷 | 可测的性质或删掉 |
| 旨在、致力于 | 它做什么 |
| 原则上、必要时、通常、一般 | 条件和判断规则 |
| 相关、相应、适当、及时、尽快 | 对象名称或时限 |
| 等、等等 | 列出项，或写「以及其余已点名的项」 |
| 优雅处理 | 实际行为（重试几次后停止） |

### 软件动词

写出可观察动作：

| 空泛写法 | 写成 |
|---|---|
| 支持 JSON | 接受 `application/json` 请求体 |
| 处理错误 | 记录错误并返回 HTTP `503 Service Unavailable` 状态码 |
| 管理会话 | 创建、读取、续期、撤销或删除会话 |
| 优化性能 | 延迟、吞吐量、内存或复杂度目标 |
| 保证安全 | 认证、授权、加密、审计或隔离要求 |

同类动作固定动词：客户端`发送`请求；服务`返回`响应或状态码；程序`读取`和`写入`存储；运行时`抛出`异常；API `返回`错误；组件`拒绝`非法输入；`重试`表示再次执行失败操作，并写明次数、间隔和停止条件。

## 句子

- 写出执行者。主语可能混淆时，把名称写出来。
- 一个规范句一项可独立测试的要求。
- 一个操作句一个动作；同时发生且不可拆分的动作可以放在一句。
- 一个说明句一个主题。一段一个主题；超过五句就检查是否混了两件事。
- 条件写在动作前面：`如果令牌已过期，认证服务必须返回……`
- 时序用「在……之前」「在……之后」「仅当……时」。
- 三项以上并列用条列；步骤用编号；各条句式对齐。
- 「它、这、其、该项、上述内容」有多个对象时，重复写出名词。
- 「和」与「或」结果不同时，写「同时满足」「至少满足一项」或「只能选择一项」。
- 范围写明是否包含端点，时间写明时区，大小写明单位。
- 例外紧跟它所限制的那条要求。
- 「正常、异常、有效、合理、足够、较大、较快」改成状态名、阈值或判断规则。

## 操作、备注、警告

- 步骤以动词开头。
- 位置不明显时，先写位置。
- `备注` 只提供信息。
- 警告先写命令或条件，再写危险、后果和预防动作。

## 标识符

- 写「`User` 对象」「`close` 方法」「`READY` 枚举值」。
- 写「发送 `POST` 请求」「返回 HTTP `401 Unauthorized` 状态码」。
- UI 标签按界面原文；操作动词与控件名称分开，例如「选择 **保存**」。

## 自查

1. 指定读者读完一遍，能否复述：谁、在什么条件下、必须做什么、结果是什么。
2. 结论或要求是否直接出现，条件是否在动作前面。
3. 有没有一句两个要求、一段两个主题、多层「的」。
4. 有没有混用 `必须 / 应 / 应该 / 应当 / 需要`，或「配置 / 设置」轮换。
5. 有没有没定义的术语、没括号说明的外文词、换成另一个名字的同一概念。
6. 事实、数字、条件、诚实的不确定是否都还在。

## 示例

**改写前**

> 登录失败时应该提示一下并做相应处理。

**改写后**

> 客户端向 `POST /sessions` 发送无效密码时，服务必须返回 HTTP `401 Unauthorized` 状态码。响应体必须包含 `code: "INVALID_CREDENTIALS"`。服务不得创建会话。
